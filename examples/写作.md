# 写作示例：完成一篇有来源的介绍文章

这是虚构情境，用来展示如何采用规范；其中的成果、来源和验证均是应执行的动作，不是已经完成的真实工作。

本例只展示一种用法；研究、分析、规划、设计、学习和日常事务等同样可以采用。

## 用户第一次怎么说

```text
请先阅读 START.md，按这套规范与我协作。
请根据当前对话中的需求选择必要的步骤和文档；缺少关键信息时问我，信息充分时按已有授权推进。

我需要一篇介绍某项新技术的中文文章，面向没有技术背景的同事，约 1200 字。资料在我上传的三份文档中。
先给我确认主题范围和结构，我确认后再写全文。不要自行发布。
```

## Agent 如何推进

1. 读取启动说明、流程的相关章节和三份资料。若有文档无法读取或说法冲突，指出会影响选题或写作的部分。
2. 按已知的读者和篇幅，交付建议的主题范围和提纲，让用户确认。
3. 用户回复“按这个结构写”后，按确认的提纲完成全文。
4. 按资料核查事实、引述和来源；查不到或超出材料范围的内容标为待核实，不添加看似真实的案例或数字。
5. 检查受众、结构、要点、长度与引用，交付正文和必要限制。发布没有获得授权，交付止于稿件。

## 使用哪些文档

- 一次性文章：任务需求、提纲、稿件和验收都可以在对话中完成，不必创建项目说明、状态文件或项目知识。
- 长期专栏：沿用已有栏目说明、风格规则和选题状态，原生项目资料或任务板已满足时不另建文件。Agent 在提纲确定、阶段稿完成等关键进展后，默认核实并保留受众与结构、稿件、待核实事实、成果位置、下一步及发布限制；完整则直接使用，不足按已授权工作只补缺项。用户换窗口后直接说“继续写下一节”等后续需求，Agent 主动读取核实上述信息再继续，不要求用户手写交接。跨产品需要时再导出注明来源和时点的交接快照。

## 多事项时怎样跟进

一次性文章通常无需编号。长期专栏同时有多个选题、修改意见或待核实问题时，Agent 按 [事项追踪](../事项追踪.md) 沿用项目已有编号和主要台账；没有合适载体时，在现有状态中补必要记录。例如某条资料口径疑问反复出现，继续更新同一事项，注明关联选题、依据和下一步，不重复建档。

疑问得到澄清时记录依据；稿件完成后仍按原验收标准检查。未获得发布授权时，编号、登记或稿件验收均不扩大到发布。

## 应如何验收

| 要求 | 应做的核对 |
|---|---|
| 面向非技术同事 | 解释必要术语，避免依赖未介绍概念 |
| 约 1200 字 | 说明字数口径，按相同口径实际统计 |
| 来源可信 | 事实与对应材料可追溯，未核实内容有标记 |
| 按确认结构写作 | 对照已确认提纲逐项检查 |
| 不自行发布 | 不执行发布操作，不把“稿件交付”写成“已发布” |
