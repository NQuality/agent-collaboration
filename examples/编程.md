# 编程示例：修复一个重复提交问题

这是虚构情境，描述应采用的协作方法。没有在本示例中实际复现缺陷、修改代码或运行测试。

本例只展示一种用法；研究、分析、规划、设计、学习和日常事务等同样可以采用。

## 用户第一次怎么说

```text
请先阅读 START.md，按这套规范与我协作。
请根据当前对话中的需求选择必要的步骤和文档；缺少关键信息时问我，信息充分时按已有授权推进。

这个项目的保存按钮连续点击会生成重复记录。请定位并修复，完成相关验证。可以修改本地项目文件，不要部署。
```

## Agent 如何推进

1. 确定当前项目，读取有效项目规则、已有运行说明与相关任务资料。只有接手旧工作时才进一步读取相关状态与决定。
2. 检查真实保存路径和现有改动，复现或通过已有代码与测试定位问题。定位后按已有授权直接修复。只有发现影响修复范围的依赖或取舍时，才专门说明下一步。
3. 使用项目现有方法修复根因，保留无关改动。若发现问题范围大于原先理解，解释证据；能独立完成的原任务范围继续。
4. 按风险执行必要验证，例如快速重复点击、保存失败后重试、正常保存。记录实际执行的方法、环境和结果，不把未运行的检查写成通过。
5. 交付变更文件、行为变化和验证结果。用户未授权部署，保留“本地已修复”和“尚未部署”的区别。

## 多事项时怎样跟进

本例只有一项修复时可以直接处理，不强制建台账。项目已有问题单或任务编号时沿用它；同时发现多个需独立跟进的问题时，按 [事项追踪](../事项追踪.md) 登记或关联已有事项，记录来源、当前状态、下一步与验证证据。代码修改完成但必要检查未做时，保持待验证。

多个窗口可在已协调的独立范围工作；共享台账的取号和更新需要串行或使用载体已验证的冲突控制。记录“某窗口处理中”只表达分工，不构成文件锁；无法协调时保留待合并内容并继续独立工作，不直接覆盖共享记录。

## 如果中途换聊天

前一阶段的 Agent 在关键进展和交付前默认检查并保留可恢复状态；用户在同项目的新会话中直接提出后续需求即可，无需另发“生成交接”或“恢复上下文”。Agent 先核实原生续做或交接、已有项目资料能否让下一次接手恢复以下信息。完整且可访问时直接使用；不足时按已授权工作补最少记录，不再新建完整状态副本：

- 当前目标及本地修改、验证授权，禁止部署的限制。
- 已定位问题的证据及相关文件。
- 已修改内容，以及当前版本或变更定位方式。
- 已运行检查的结果；尚未执行的场景及原因。
- 下一步，例如补做失败重试验证；原授权仍然有效。

跨产品时可按需导出带来源、时间或版本的快照，不要求在原生交接和文档间长期手动同步。新 Agent 收到后续需求后，主动从已选来源或快照读取状态，核对当前文件和证据是否仍匹配，继续已授权工作。发现另一个人修改了相同位置时，先重读并核对，能够安全合并则继续；不能确定的冲突留给用户判断，避免覆盖。

## 使用哪些文档

复用已有项目规则与运行说明；需求和短计划可在对话或原生工具中。跨会话时核实主要状态来源能否满足接手，必要时补缺或导出，不默认新建状态文件。用户要求沉淀方法时，先检查是否已有适用流程，再补充必要内容。

需要模板时参考 [当前状态与交接](../templates/05-当前状态与交接.md)、[验收与交付](../templates/07-验收与交付.md)。
